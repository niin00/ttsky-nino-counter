| **`test` workflow failed on first push.** CI error: `assert dut.uo_out.value == 1` fails, actual `0`, after one full clock period with `ui_in[0]` held high. Message reads exactly like an RTL bug (counter not incrementing). **Real cause (confirmed by trace, not by trial-and-error): a cocotb 2.0 write-scheduling race in my testbench**, not the RTL. Coroutines resuming from `await ClockCycles(...)` do so in the simulator's ReadOnly phase; any `.value =` write issued right then is deferred to the next scheduled write phase — which coincides with the *next rising edge itself* in this Makefile/clock setup, racing against the flop's own edge-triggered sample. The old value wins the race, so every input change made immediately after an edge-await takes effect one full cycle later than intended. Fix: insert `await Timer(1, unit="ns")` right after any `.value=` write, before awaiting the next edge, to force the write into its own distinct, earlier time step. | AI got it subtly wrong initially, root-caused and fixed with reasoning (not guess-and-check) — flagging as **uncertain/inferred, not verified against cocotb source** | **Yes, very likely, and this is the single most valuable finding in this log.** The template's own placeholder design (`uo_out = ui_in + uio_in`) is purely combinational, so its example test never exercises a clock-edge race — this bites the instant anyone writes a registered/sequential design (i.e. almost any real ASIC submission) and follows the template's own testbench idiom literally. **Gap between CI error and real cause: the assertion failure reads as "your counter doesn't count," not "your test's write timing races the clock edge" — nothing in the log or template docs hints at cocotb 2.0's write-scheduling semantics.** Docs are silent on this entirely as far as I've seen in this template. |
